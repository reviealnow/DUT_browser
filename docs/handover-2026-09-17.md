# Handover — 2026-09-16/17: reaching a DUT console through a Raspberry Pi

Written for the next session, which will have none of this context.

**The headline: SSH password login from this dashboard had never worked.** Not
"broke recently" — the transport could not ask for a password at all, and every
attempt was reported to the operator as a refused credential. That was found and
fixed here, and with it the whole path works: Mac → SSH → Raspberry Pi → `socat`
→ DUT serial line, carrying both console output and sysMon telemetry.

Everything else in this file is either a consequence of chasing that, or an
interface that claimed more than it had measured.

## What landed

Sixteen PRs merged into `CPU_Plots` (`a0b811b`…`cb2a91f`). Two of them (#170,
#171) came from a parallel session.

### The bug that was actually blocking the bench

**#175** — `spawn_with_tty` closed the pty **slave** in the parent, and real ssh
runs `closefrom()` before it prompts. By the time it wanted a password there was
no controlling terminal left: `open("/dev/tty")` returned ENXIO and ssh gave up
**without sending an authentication request at all**. sshd logged only
`Connection closed by authenticating user [preauth]`, never a failed password,
while the card said the credentials were refused. The parent holds the slave now.

Why no test caught it: the fake ssh in the suite opened `/dev/tty` as its first
act and never closed an inherited descriptor, so it held the last reference to
its own terminal. It models `closefrom()` now, which turns **14 of that file's
18 tests red** against the old code.

### Labels that claimed more than they knew

A theme rather than a coincidence — each said something the app had not measured:

| PR | Claimed | Actually meant |
|---|---|---|
| #173 | `Ready` beside a failed login | `ready` = "a password is held", which survives a failure |
| #174 | "The collector refused these credentials" | three different ssh refusals flattened into one sentence |
| #178 | "Step 1 — select a serial port" over a streaming DUT | the page only knew about sessions **it** had opened |
| #179 | `Attached here as …` forever, Detach doing nothing visible | attachment was computed from the *registration*, not from an open console |
| #182 | `No DUT` | "nothing has arrived for ten seconds" — a held, quiet console read as absent |
| #184 | a switcher missing a DUT whose console worked | only Settings ever told the shell the registry had changed |

### Features

- **#169** Fleet became a sidebar group: *DUTs & Mesh* / *Hosts* / *Profiles*.
  Hosts is the collectors card rebuilt as one card per box — the separate
  registration form is gone, because a card *is* the editor. Profiles are saved
  host settings with a scope and an owner, and **never a password**.
- **#177** `Send Enter` — the command box refuses an empty value on purpose, and
  a bare newline is the one thing you want to send to a silent console.
- **#180** One breathing dot, drawn only where something is live.
- **#183** Trust a host key from the card: it shows what is on record and what
  the box presents, and the Trust button **names a fingerprint** — the backend
  re-reads the host and writes only if it still matches. It refuses when a key is
  already on record, so `ssh-keygen -R` stays a deliberate act.
- **#176** `tools/bench_ssh_login.py` — the tracer that found #175, kept.
- **#181** README and docs: three files still told operators to click a card
  that had been retired.

## Open items

### For the operator, on the bench

1. **Two interfaces on one subnet.** *Half wrong -- corrected 2026-09-17.*
   **Do not run `sudo ifconfig en5 down`.** That instruction was here, and it
   would now break the one path that works.

   What still holds: `en0` = 192.168.30.144, `en5` = 192.168.30.164, and the
   route for `192.168.30.0/24` goes via `en5` (`en0`'s copy of it is
   `IFSCOPE`d). What does not hold is that `en5` is dead. Measured 2026-09-17:
   it is `UP,RUNNING`, `1000baseT <full-duplex>`, it reaches the gateway at
   **0% packet loss**, and it is the interface carrying all five live SSH
   sessions on the bench -- the backend's four (two per Pi: the collector
   shell and the `socat` console) opened *from* 192.168.30.164 between 16:09
   and 16:13 that day, plus one hand-run `ssh pi@192.168.30.145` from 15:25.
   Four successful opens in that window disprove "new connections fail".

   The symptom is real but it is not on this Mac. At 16:18 the same day, with
   those sessions still established:

   * `192.168.30.145` answered ARP (`b8:27:eb:...`, the Pi Foundation OUI) --
     its NIC is alive -- while ICMP echo and a fresh TCP SYN to 22 both got
     nothing;
   * `192.168.30.124` answered nothing at all: ARP `(incomplete)`.

   Ruled out from here: the source interface (`nc -s` from **both** .144 and
   .164 fails identically), the routing (`route get` resolves, and the gateway
   answers over that route), and the shell doing the probing (the same command
   reaches the gateway's 80 and 443). An L2-alive box that answers ARP, keeps
   established connections and drops new SYNs is a *far-end* state -- a
   firewall permitting only ESTABLISHED, a wedged IP stack, or the switch port
   -- and it has to be diagnosed on the Pi, not on the Mac. `Verify` and the
   host-key scan stay broken until it is.
2. **sysMon stops on its own.** *Wrong -- corrected 2026-09-17: it does not.*
   The log this claim came from,
   `logs/dut-session-192.168.30.124ttyUSB0-20260916-115810.log`, opens with
   `Step: 60s (60s), Duration: 30m (1800s)` and closes with
   `= Test finished @ 2026-09-16 05:18:13`. It was asked for thirty minutes and
   it ran thirty minutes: 24 cycles, a measured 79 s apart, is 31.6 minutes.
   The charts go quiet because the run **ended**, not because anything failed.

   What to do differently is still "pass a longer `<duration>`", but the reason
   matters for planning a run: **the period is not the `<step>`.** Measured
   overhead is **+19 s** per cycle on an idle DUT and **+63 s** on a loaded one
   (worst single gap 270 s). `curl_hooks` alone sleeps 8 s, `cpu_utilization`
   and `interrupt_softirq_analysis` a second each, and `process_details_all`
   walks every `/proc/<pid>`. A `30s` step yields a cycle every 49-93 s.
3. **Merged local branches can be removed** — twenty of them, plus a stale
   `DUT_browser-env` worktree. Deletion is the operator's action (a hook
   enforces it), so the commands live here rather than being run:
   `git branch -d <name>` and `git worktree remove ../DUT_browser-env`.

### Product work, in rough order of value

1. **`deleteFile` and `removeDut` bypass `fail()`** (`frontend/src/api/rest.ts`).
   They throw the response text directly, so a 401 on either does **not** fire
   the unauthorized event that signs a stale session out. `del()` now exists
   beside them and `removeCollector` uses it; these two were left alone because
   the change is about them, not about the PR that noticed it.
2. **The host-key panel is only inside Details.** A login that fails on an
   unknown key still tells the operator to expand a section they may not know
   exists. Surfacing the panel automatically on that specific failure is the
   obvious follow-up.
3. **`known_hosts` belongs to whoever runs the backend.** `hostkey.trust` writes
   `~/.ssh/known_hosts` for the backend's user. Running the service as another
   user (systemd, a service account) silently writes somewhere the operator's own
   `ssh` will never read. Worth showing the resolved path in the UI.
4. **The demo kit has no fixture in the `Connected` state.** Both pages implement
   the rule from #182, so they cannot drift on *when* the word applies, but the
   kit cannot *show* it: every `idle` DUT there has `open: false`. Adding one is
   a decision about what the kit portrays, so it was not smuggled in.
5. **The toolbar squeezes at ~900px** — title and subtitle wrap to one word per
   line between the drawer breakpoint and roughly 1100px. Pre-existing, on every
   section, unrelated to this work.
6. **`FleetCard` prints two rows that now agree** for a remote DUT with an open,
   quiet console: `SSH session: Connected` and `Node console: Connected`. Not
   wrong, but one of them has stopped earning its line.
7. **A derived collector id picked up a `-2` suffix** (`pi2-2`) when nothing
   obviously held `pi2`. Probably a removed-then-re-added host; worth a look
   before somebody reads the suffix as a second box.

## How to verify the whole path again

```bash
# 1. the network must actually reach the box.
#    NOT ping: neither Pi answers ICMP even when the path is perfectly healthy,
#    so an echo timeout says nothing. Measured 2026-09-17: 192.168.30.145 had a
#    good ARP entry (b8:27:eb:..., the Pi Foundation OUI), a reachable sshd and
#    five live sessions from the backend, while every echo request timed out.
#    Probe the port the app actually uses.
nc -z -G4 <pi-address> 22 && echo "TCP/22 reachable"

# 2. the transport, from the app's own code, with a trace
cd dut-dashboard/backend
../../.venv/bin/python ../tools/bench_ssh_login.py <pi-address> <user>
```

Then, in the app, as admin: **Fleet ▸ Hosts** → the host card → `Verify` →
`Attach` the serial device → **Serial Console** (it reports *Connected* on its
own now) → `Send Enter` if the console is silent. The session log grows under
`dut-dashboard/logs/dut-session-<host><device>-*.log`; parsed telemetry lands in
`snapshots-<dut-id>.jsonl` and stays empty until sysMon runs on the DUT.
